Payment API Integration: Handling Timeouts, Retries, and Reconciliation

A lost response is not proof of a failed payment. Keep uncertainty visible, prevent duplicate operations, and reconcile against independent evidence.

Bring the workflow, its owners, and a clear definition of completion.

Payment API integration connects a business application with a payment provider while maintaining a trustworthy record of what was requested, what the provider confirmed, and what eventually settled. Handling timeouts, retries, and reconciliation is central to that record.

When a payment request times out, the caller knows it did not receive a complete response. It may not know whether the provider received, processed, or completed the operation. Treating that uncertainty as a decline can lead to a second charge; treating it as success can trigger premature fulfilment.

This guide expands our partner-payment article with a hypothetical order, a recovery policy, and a reconciliation process. For the wider system boundaries, begin with connecting legacy ERP, CRM, and partner systems. The states below are an application model, not a replacement for any provider’s documented lifecycle.

Keep transport state separate from payment state

A successful HTTP exchange and a successful financial operation are different facts. An accepted request may still require customer action, asynchronous processing, or later capture. Similarly, a network exception does not establish that no money moved.

Stripe’s PaymentIntent lifecycle (opens in a new tab) illustrates why an integration needs more than a paid/unpaid flag. Map provider-specific statuses into your application explicitly, preserving the original status and resource ID for investigation.

Record authorisation, capture, refund, and settlement separately when your payment method distinguishes them. A captured charge can later be refunded or disputed; those are additional operations and ledger entries, not a reason to erase the original evidence. Agree which stage permits dispatch, account activation, or partner credit.

Worked example: the provider accepted the payment, but the response was lost

Imagine order ORD-1042 for INR 1,250.00. The amount is fictional. The provider in this example supports idempotent creation with a retained operation key and a resource-status endpoint. Check those capabilities before adopting this recovery path.

  1. Before dispatch: persist operation PAY-1042-A, amount 125000 paise, currency INR, request fingerprint, and a random idempotency key. A database uniqueness rule prevents two workers from claiming the same charge intent.
  2. The request leaves: the provider creates payment resource P-778. The response is lost between the provider and your application. Your client’s illustrative five-second deadline expires.
  3. The application records Unknown: keep the original key and payload. Show “Payment confirmation pending” and prevent a second submission for the same active intent. Do not mark the order paid or tell the customer the payment definitely failed.
  4. A recovery worker resolves it: if the resource ID is known, query its status. If it is not known and the provider documents safe replay for this failure, retry the same operation with the same key and unchanged parameters within the supported retention window.
  5. Confirmation arrives: the replay returns P-778, or an authenticated callback identifies it. A conditional state transition and a unique business-effect key ensure the order is fulfilled once.
  6. Finance verifies later: compare the provider’s records with the payment operation and the internal ledger. A later refund or settlement adjustment has its own evidence and accounting treatment.

If the provider supports neither reliable status retrieval nor safe duplicate prevention, stop automatic replay after an ambiguous write. Route the operation to an investigation queue with the provider reference, timestamps, and request ID. Asking the customer to click Pay again is not a recovery strategy.

Make the key identify one business operation

An idempotency key lets a provider recognise a repeated operation according to its own contract. Persist it before sending the request. Scope it to the merchant account and operation type; capture, refund, and charge creation must not accidentally share one intent.

Stripe’s idempotent-request reference (opens in a new tab) documents saved responses, parameter matching, and key pruning after at least 24 hours. That window is Stripe-specific. Your internal duplicate guard should cover your own business replay window even after an external key expires.

PayPal’s idempotency guidance (opens in a new tab) uses PayPal-Request-Id, with support and retention determined by the API. Adyen’s idempotency reference (opens in a new tab) also describes provider-specific retry signals. Write a capability matrix for each endpoint instead of assuming one payment-provider abstraction gives them identical guarantees.

Use a new key only for a genuinely new operation. A changed amount requires a controlled new attempt after the earlier intent is resolved or safely cancelled. Store the request fingerprint, attempt count, last outcome, and resource reference so an operator can explain why a replay is safe.

The database still has a job

Provider idempotency does not prevent your application from fulfilling an order twice, adding duplicate ledger entries, or processing the same callback twice. Protect those local effects independently.

Classify the failure before scheduling a retry

Define connection, read, and total deadlines. Choose them from measured provider latency and the customer’s acceptable wait, not from an arbitrary long timeout. Account for retry behavior already built into the SDK: an application retry wrapped around SDK retries can multiply requests.

Stripe’s advanced error handling (opens in a new tab) treats certain server errors as indeterminate and warns against retrying with a new key. A repeated cached error is not evidence that the original request had no side effects. Follow the endpoint’s documented recovery behavior.

A proposed background policy might use capped exponential delay with jitter, a maximum attempt count, and an overall resolution deadline. These are design parameters to test. Stop automatic retries when safety cannot be established, and escalate overdue unknowns rather than deleting them.

HTTP’s Retry-After definition (opens in a new tab) explains the header’s timing formats. Do not retry earlier than a valid provider instruction. A circuit breaker (opens in a new tab) can reduce calls to an unhealthy dependency, but opening it does not resolve operations already sent.

Treat callbacks as evidence that needs validation

Verify the provider’s signature using the required original payload and secret. Persist the accepted event durably before acknowledging delivery, then process it asynchronously. If durable acceptance fails, return an appropriate failure so the sender can follow its delivery policy.

Stripe’s webhook documentation (opens in a new tab) covers signature verification, duplicate events, and delivery without guaranteed order. Deduplicate by the documented event identity, then separately guard business effects: multiple different events can refer to one payment.

A late processing notification must not overwrite a later confirmed capture. Apply valid lifecycle transitions; retrieve the current provider resource when event order leaves the state unclear. Keep refunds and disputes distinct from the charge’s success state. This is a useful application of the API and event-driven integration tradeoffs.

Reconcile the operation, the provider record, and the ledger

Reconciliation checks whether independent records describe the same financial activity. Confirmation of one charge does not prove that fees, refunds, settlement, and bank deposits all match. Build an exception process alongside the matching job.

Match by merchant account, provider resource ID, internal operation ID, amount, and currency. Retain the original transaction date and the report’s settlement date or timezone. Avoid floating-point arithmetic for monetary comparisons; use the provider’s currency-unit rules and separate currencies in totals.

Stripe’s balance transaction types (opens in a new tab) distinguish categories such as charges, refunds, fees, and adjustments. Stripe’s bank reconciliation documentation (opens in a new tab) describes reconciling cash movements with bank statements. Choose reports and reconciliation boundaries available to your own account and provider.

  • Missing internal record: investigate an external payment with no matching operation; do not silently insert a guessed order association.
  • Missing external record: distinguish reporting delay from an incorrectly confirmed local payment.
  • Amount or currency mismatch: compare the original intent, capture, partial refund, fee treatment, and exchange-rate handling.
  • Duplicate effect: check whether duplicate ledger entries represent one charge or two separate provider operations.

Set an owner, ageing threshold, and correction approval for every exception category. Re-running a report should update the same exception, not create a new unresolved ticket each day. Preserve a correction history; never erase evidence to force totals to match.

Protect credentials and make investigation possible

Keep payment credentials on the server, restrict permission by operation, and redact sensitive payloads from logs. Verify object-level access before exposing a payment status to a user. OWASP’s object-level authorisation guidance (opens in a new tab) describes the access checks that resource identifiers require.

Log correlation IDs, attempt timing, classified error, and state transitions without storing raw card data or secrets. Track the oldest unknown payment, callback-processing delay, retry volume, and reconciliation exceptions. OpenTelemetry’s signals overview (opens in a new tab) separates traces, metrics, and logs; connect those signals using the business operation reference.

Test the paths that ordinary happy-path demos miss

  • Lose the response after a simulated provider acceptance. Verify Unknown, stable keys, and no duplicate fulfilment.
  • Crash the worker before dispatch and after dispatch. Recover from durable intent without guessing whether the request left.
  • Deliver duplicate callbacks and callbacks in reverse order. Verify valid state transitions and one local effect.
  • Return throttling and prolonged server errors. Check retry caps, escalation, and customer messaging.
  • Re-run the same settlement file, omit a record, and introduce a partial refund. Check exception deduplication and accounting ownership.
  • Attempt status access from another customer account. Confirm authorisation and log redaction.

Common questions about payment API integration

Should every timed-out payment be retried?

No. Retry a write only when the provider’s duplicate-prevention and failure semantics make replay safe. Otherwise resolve its status or investigate it. A timeout alone is not a decline.

Does an idempotency key guarantee exactly-once payment handling?

It addresses repeated provider requests within a documented scope and retention window. Your state store, ledger, callback worker, and fulfilment process still need their own duplicate protection.

Can webhooks replace reconciliation?

No. Webhooks help update operational state. Reconciliation compares independent financial records and catches missing entries, fees, settlement differences, and adjustments.
