Incremental Legacy Modernization: Applying the Strangler Fig Pattern

Replace one business capability behind a controlled boundary. Keep retained functions operating while you validate data, behavior, and ownership.

Bring the workflow, its owners, and a clear definition of completion.

Incremental legacy modernization applies the Strangler Fig pattern by replacing selected capabilities gradually, routing each migrated operation to its new implementation while the legacy system continues to serve the rest.

The pattern needs more than a new API in front of old code. You must identify meaningful boundaries, preserve contract behavior, control write authority, and establish evidence that each replacement can operate independently.

This guide develops a hypothetical customer-profile replacement with routing, data, release, and retirement decisions. It describes proposals to validate, not a deployed NMIT case study. If your goal is to keep existing applications connected rather than replace their functions, start with our legacy system integration guide.

Use the pattern when coexistence and controlled interception are feasible

Martin Fowler’s Strangler Fig explanation (opens in a new tab) describes gradual replacement. Microsoft’s pattern guidance (opens in a new tab) describes a façade that routes work between retained and new implementations. The business-facing interface can remain stable while responsibility moves behind it.

Assess interception and internal dependencies before choosing this approach. A vendor-controlled application may not let you redirect its internal calls or disable migrated functions. A small replaceable system or a mandatory near-term shutdown can make extended coexistence unsuitable.

AWS Strangler Fig guidance (opens in a new tab) discusses incremental decomposition and its considerations. Do not assume every modernization should end in many microservices. A well-bounded replacement can be a module or service whose operating complexity matches the team.

Record the intended endpoint: selected replacement, full retirement, or long-term coexistence. If the legacy system will remain, define its continuing contract and ownership rather than describing every retained dependency as temporary.

Coexistence creates work

Two implementations, transition adapters, routing policies, and data synchronization need testing and ownership. They can reduce the size of each change while adding temporary operating obligations.

Choose a capability with a measurable outcome and a defensible boundary

Pick a business capability such as viewing an approved customer profile, rather than extracting arbitrary tables or controller files. Identify its consumers, data authority, permissions, transaction boundaries, and dependencies on unmigrated functions.

Map infrequent jobs, reports, and partner calls too. The hybrid dependency checklist helps expose paths that normal web traffic misses. Record what discovery observed and which paths still need owner confirmation.

Prioritize a slice whose value and risk are clear. Choosing the least used screen can make a pilot easy without providing evidence about the difficult dependencies that govern later work. Choosing the largest financial write first can make recovery unnecessarily complex.

Make routing an explicit, versioned operating decision

Define which capability, consumer, or approved cohort uses the replacement. Keep policy reviewable and observable. A route change must preserve authentication, object-level authorisation, required headers, and error semantics.

OpenAPI (opens in a new tab) can describe the HTTP contract. Compare meaningful behavior as well as payload shape: missing fields, explicit clears, pagination, identity scope, and the stage represented by a success response.

When semantics differ, use a focused translation boundary. Microsoft’s anti-corruption-layer pattern (opens in a new tab) describes protecting one model from another’s conventions. Decide whether that adapter is transitional or an ongoing integration responsibility.

Monitor the router itself for availability, latency, and policy failures. It can become a bottleneck. Retained functions must still work when a replacement is unavailable; define the permitted fallback without assuming all writes can be sent back safely.

Separate implementation routing from data authority

A request reaching the new service does not automatically make its database authoritative. Document where each entity and field is read and written during every transition stage. Preserve stable identity and track versions within their source scope.

For a read-only replacement, an approved replicated view can be useful if freshness and access rules fit the business. For a writer transition, plan the initial load, catch-up boundary, in-flight work, and the point at which the old writer is fenced.

Avoid uncontrolled dual writes. One system can succeed while the other fails, producing divergent records. Where you control the source transaction, the transactional outbox pattern (opens in a new tab) can persist a change and outgoing message together. The relay and consumer still need duplicate-safe effects.

AsyncAPI (opens in a new tab) can describe event contracts. Define event identity, schema version, source meaning, retention, and replay permissions separately. A published event is not proof every consumer has applied it.

Worked example: replace the customer-profile read before its writer

Imagine a fictional legacy portal where profile reads and billing changes share an old application. The initial replacement provides an approved customer-summary read. Finance remains authoritative for billing fields. This is one possible slice, not a prescription for every application.

  1. Document the read contract: identity scope, fields, permissions, freshness, and missing-record behavior.
  2. Build the replacement: use the agreed source interface or replicated view, keeping source identity and freshness visible.
  3. Compare safe reads: evaluate representative outputs without exposing production personal data or invoking write side effects.
  4. Route a controlled group: observe contract equivalence, end-to-end response, stale-data behavior, and fallback limits.
  5. Expand the read boundary: move confirmed consumers while retaining unmigrated writers and documenting their connections.
  6. Plan a later writer move: treat write authority, data transfer, fencing, and correction as a separate release decision.

Do not use shadow writes to compare implementations by creating real duplicate effects. Read comparison also needs privacy, capacity, and partner approval considerations. A new response containing more fields can be a security regression even if it is faster.

OWASP’s object-level authorisation guidance (opens in a new tab) supports checking each resource access. Preserve those checks on both routes rather than relying on the façade’s existence.

Validate behavior and recovery before expanding responsibility

Keep a contract test suite for retained and replacement behavior. Exercise invalid identity, stale data, unavailable dependencies, concurrency, and version conflicts. For financial capabilities, use the cases in our payment failure-testing checklist.

Microsoft’s safe-deployment guidance (opens in a new tab) supports controlled rollout and health evaluation. Its reliability-testing guidance (opens in a new tab) covers fault and recovery validation. Set workload-specific stop conditions before release.

Keep route identity in bounded telemetry dimensions and business operation records. The W3C Trace Context standard (opens in a new tab) helps correlate instrumented requests; sampled traces do not replace durable evidence.

Routing back after a read replacement can differ substantially from returning a writer. Once the replacement accepts writes, the legacy store may be stale or lack compatible semantics. A valid rollback needs reconciled state and accounting for external effects, not just the prior route configuration.

Review complete business outcomes with our integration monitoring guide. Google’s monitoring chapter (opens in a new tab) adds diagnostic context, but a technically healthy router cannot establish a correct customer record.

Retire a legacy capability only after its dependencies are resolved

  • All intended consumers and internal callers use the approved replacement path.
  • Scheduled jobs, reports, partner callbacks, and recovery paths were reviewed.
  • Data authority, history retention, and correction responsibility are agreed.
  • Replacement behavior and recovery were validated against the accepted contract.
  • New writes and external side effects are accounted for in recovery procedures.
  • Receiving-team documentation, access, and escalation are accepted.
  • Removal of code, data objects, routes, and credentials follows approved retention and change processes.

A retained façade may still serve older clients; define its owner and lifecycle. Removing legacy tables too early can make recovery significantly harder. Preserve the evidence behind each retirement decision and keep known retained dependencies visible.

Budget the transition and hand over both routes

Include coexistence environments, adapters, routing, contract tests, reconciliation, instrumentation, and recovery drills in the project-cost scope. Temporary infrastructure is still infrastructure that somebody must operate.

Use the integration handover checklist before responsibility expands. The receiving team needs to explain which implementation and data owner served an operation, and what can safely happen if it fails.

Common questions about the Strangler Fig pattern

Does incremental modernization require microservices?

No. The essential mechanism is gradual capability replacement behind controlled boundaries. Choose an implementation structure the team can operate.

Can both implementations write the same record?

Only through an explicitly designed authority and consistency mechanism. Uncontrolled dual writes can diverge after partial failures.

When can the legacy function be removed?

After its consumers, data, recovery paths, and operating responsibility are accounted for and accepted. A responding replacement endpoint alone is insufficient evidence.
